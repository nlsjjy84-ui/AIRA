# Correction / History Presentation Boundary v1

## Core rule
A later correction, revision, or replacement filing never erases the historical existence of the earlier provider record.

## Product meaning
- preserve prior Evidence/Fact/Event history unless an explicit existing AIRA contract says otherwise;
- when official lineage is proven, show earlier and later records as related versions/corrections, not as if the earlier record never existed;
- if lineage is not officially proven, keep separate records and do not infer supersession from titles, labels, or chronology alone;
- the newest visible record is not automatically the only valid historical record.

## User-facing restraint
Inspect/Relate/Assess may distinguish `current/latest`, `historical`, `corrected`, or `conflicting` states only when the underlying contract/evidence supports that label.
Do not hide previous values merely because a newer filing exists.

## Implementation boundary
Revision lineage tables, supersession links, current-selection queries, UI history controls, and tests are CODEX-FIRST/later work.
