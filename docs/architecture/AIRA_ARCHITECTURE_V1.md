# AIRA Architecture v1

- 상태: Approved
- 버전: 1.0
- 기준일: 2026-08-14
- 대상: AIRA 제품, 데이터, 애플리케이션 및 운영 아키텍처

## 1. 목적과 제품 정의

AIRA는 공개 시장 정보를 발견하고 출처를 확인한 뒤, 사건 단위로 통합·분석하여 사용자의 관심과 관련된 정보만 근거와 함께 전달하는 정보 엔진이다.

AIRA는 단순 검색 엔진, 범용 AI 챗봇 또는 매수·매도 판단기가 아니다. 사용자의 투자 결정을 대신하지 않으며, 판단에 사용된 근거와 불확실성을 사용자가 확인할 수 있게 한다.

기본 처리 흐름은 다음과 같다.

```text
정보 발견 → 출처 확인 → 사건 단위 정리 → 중요성 분석
         → 사용자 관심과 연결 → Briefing / Alert 전달
```

이 문서에서 요구 수준은 다음과 같이 해석한다.

- **MUST**: 보안, 개인정보, 데이터 신뢰성 또는 핵심 제품 정체성을 위해 반드시 준수한다.
- **SHOULD**: 특별한 근거가 없다면 준수한다. 예외는 문서화한다.
- **FUTURE**: 확장 가능성은 보존하되 v1에서 선행 구현하지 않는다.

## 2. 최상위 원칙

1. **MUST** 필요 없는 정보를 사용자에게 전달하지 않는다.
2. **MUST** 서비스 목적에 필요 없는 데이터를 수집하지 않는다.
3. **MUST** 필요 없는 AI 연산과 토큰을 사용하지 않는다.
4. **MUST** 외부에서 확인 가능한 사실과 AIRA 또는 AI의 해석을 분리한다.
5. **MUST** 매수·매도 등 사용자의 투자 결정을 대신하지 않는다.
6. **MUST** 사용자가 판단 근거와 불확실성을 확인할 수 있게 한다.
7. **MUST** 보안과 AI 토큰·비용을 핵심 운영 위험으로 관리한다.
8. **SHOULD** 1인 개발·운영이 가능한 단순성을 유지하면서 팀과 데이터 규모 증가에 대응한다.
9. **MUST** 미래 확장성을 이유로 현재 필요하지 않은 기능과 데이터를 과잉 구현하지 않는다.

## 3. 범위

### 3.1 v1 우선 범위

- 기업 및 종목 관련 뉴스
- 공시
- 시장에 영향을 미치는 주요 사건
- 사건의 근거, 중요성 및 가능한 영향 분석
- 사용자 관심과 연결된 Briefing 및 가치 기반 Alert

### 3.2 FUTURE

- 경제지표, 정책, 지정학, 산업 및 원자재로 정보 범위 확장
- 가상투자
- 고도화된 개인화
- 교육 기능
- 필요성이 검증된 도메인의 독립 서비스 분리

FUTURE 항목은 핵심 정보 엔진보다 먼저 구현하지 않는다.

## 4. 시스템 구조와 경계

v1은 **modular monolith**를 기본 배포 형태로 사용한다. 수집, 사건, 근거, 분석, 사용자, 인증, 전달 및 AI 운영의 책임은 논리적으로 분리한다. 처음부터 마이크로서비스로 나누지 않지만, 모듈 간 계약과 데이터 소유권을 명확히 하여 향후 필요한 경계만 분리할 수 있게 한다.

```text
공개 정보 공급자
      │
      ▼
수집 → 정규화 → 중복 제거 → Source / Evidence
                               │
                               ▼
                         Event ↔ Entity
                               │
                               ▼
                      Assessment → Impact → Entity
                               │
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
              Briefing                     Alert
                 ▲                           ▲
                 └──── UserInterest / User ──┘

독립 운영 경계: Authentication / Session, AIExecution / Token / Cost
```

모듈은 다른 모듈의 내부 구현에 직접 결합하지 않고 명시적인 애플리케이션 계약을 통해 협력해야 한다. 특정 AI 모델이나 데이터 공급자 하나의 형식이 핵심 도메인 모델로 누출되어서는 안 된다.

## 5. 핵심 도메인 모델

### 5.1 Source와 Evidence

`Source`는 정보를 제공하거나 발행한 주체다. `Evidence`는 AIRA가 Event 구성이나 Assessment 판단에 실제로 사용한 외부 근거다.

- **MUST** 하나의 Event에 여러 Evidence를 연결할 수 있어야 한다.
- **MUST** AI가 생성한 문장을 Evidence로 취급하지 않는다.
- **MUST** Evidence의 원문 출처와 사용한 부분을 가능한 범위에서 추적할 수 있어야 한다.
- **MUST** 출처를 단일 절대 신뢰도 숫자로 환원하지 않는다.
- **SHOULD** 출처 유형, 원문 위치, 발행 시각, 수집 시각 및 변경 여부 등 판단 문맥을 보존한다.

### 5.2 Event

Event는 AIRA 정보 모델의 중심이다. 같은 사건을 다룬 기사, 공시와 기업 IR은 중복 문서가 아니라 가능한 경우 하나의 Event와 여러 Evidence로 통합한다.

v1 Event 유형은 다음과 같다.

- `EARNINGS`
- `DISCLOSURE`
- `BUSINESS`
- `GOVERNANCE`
- `POLICY_REGULATION`
- `RISK`
- `MARKET`

- **MUST** Event에 매수·매도 지시를 저장하지 않는다.
- **MUST** Event 자체에 단일 호재·악재 또는 positive·negative 값을 저장하지 않는다.
- **SHOULD** Event 통합 과정과 중복 판단을 추적 가능하게 한다.

### 5.3 Entity

Entity는 AIRA가 추적하는 공개 시장 대상이다. 기업, 증권·종목, 산업, 시장, 국가 및 원자재 등이 될 수 있다.

- **MUST** Event와 Entity의 다대다 관계를 지원한다.
- **MUST** 일반 사용자를 시장 Entity로 모델링하지 않는다.
- **MUST** 공개 시장 데이터와 개인 사용자 데이터를 논리적·접근제어 관점에서 분리한다.

### 5.4 Assessment와 Impact

Assessment는 사실 자체가 아니라 Event의 중요성과 가능한 영향을 분석한 결과다. 중요도, 분석 요약, 확신 수준, 불확실성, 시간 범위와 분석 상태를 표현할 수 있어야 한다.

Impact는 특정 Assessment가 특정 Entity에 미칠 수 있는 영향을 표현한다.

```text
Event → Assessment → Impact → Entity
```

- **MUST** 불확실한 내용을 확정 사실처럼 표현하지 않는다.
- **MUST** Assessment를 매수·매도 지시로 변환하지 않는다.
- **MUST** Entity별로 다른 영향을 Impact에 표현한다.
- **MUST** Evidence와 Assessment 사이의 추적 관계를 유지한다.

## 6. 사용자, Briefing과 Alert

### 6.1 User와 UserInterest

User는 사람에 관한 정보를 최대한 저장하는 대상이 아니라 계정 운영에 필요한 최소 정보를 나타낸다. UserInterest는 공개 시장 Entity 또는 관심 범위와 사용자를 연결한다.

- **MUST** 일반 사용자 데이터와 인증정보를 분리한다.
- **MUST** UserInterest를 이유로 공통 Event와 Assessment를 사용자별로 복제하지 않는다.
- **SHOULD** 공통 분석은 재사용하고 선택·정렬·전달만 필요한 수준에서 개인화한다.

### 6.2 Briefing

Briefing은 기존 Event와 Assessment를 재사용하여 중요한 변화, 관심 분야의 변화, 추가 확인이 필요한 사건과 향후 일정을 압축해 제공한다.

- **MUST** 동일한 공통 내용을 사용자마다 AI로 다시 생성하지 않는다.
- **SHOULD** 즉시성이 낮은 정보는 Alert 대신 Briefing으로 묶는다.

### 6.3 Alert

새 정보의 발생만으로 Alert를 보내지 않는다. Event 중요도, Evidence 수준, Entity 관련성, 시간 민감도, 사용자 관심과 기존 알림 중복을 함께 고려한다.

- **MUST** “지금 사용자에게 알리는 것이 실제 가치가 있는가”를 평가한다.
- **MUST** Alert 정책을 버전 관리하고 발송 이유를 사후 추적할 수 있게 한다.
- **SHOULD** 중복·저가치 알림을 억제한다.

## 7. AI 실행과 비용 통제

AI 사용 가능성은 AI 호출의 충분한 이유가 아니다. 기본 처리 순서는 다음과 같다.

```text
수집 → 정규화 → 중복 제거 → 규칙 기반 처리 → 기존 결과/캐시 확인
    → 중요도 판단 → 필요한 경우에만 AI → 결과 저장 및 재사용
```

- **MUST** 동일 데이터를 불필요하게 반복 분석하지 않는다.
- **MUST** 사용자 수만큼 동일한 공통 분석을 반복하지 않는다.
- **MUST** 민감정보, API Key와 인증 토큰을 프롬프트 또는 AI 로그에 저장하지 않는다.
- **SHOULD** 특정 공급자와 모델을 교체할 수 있는 경계를 둔다.
- **SHOULD** AI 결과에 prompt/version과 입력 근거를 연결한다.

AIExecution은 최소한 다음 운영 정보를 추적할 수 있어야 한다.

- provider, model, task type, prompt/version
- input tokens, output tokens
- estimated cost 및 가능한 경우 actual cost
- latency, success/failure, cache hit 여부

장기적으로 기능별, 모델별, 일별, 월별 및 사용자당 비용을 관찰할 수 있어야 한다. 사용자당 비용은 공통 분석 비용을 사용자별로 중복 발생시키라는 의미가 아니다.

## 8. 개인정보와 데이터 최소화

새로운 사용자 데이터 수집 전 다음을 검토하고 기록해야 한다.

1. 왜 필요한가?
2. 더 적은 데이터로 가능한가?
3. 어디에 저장하는가?
4. 누가 접근하는가?
5. 얼마나 보관하는가?
6. 언제 삭제하는가?

필요성이 입증되지 않으면 실명, 성별, 생년월일, 주소, 직업과 전화번호를 미래 사용 가능성만으로 수집하지 않는다.

현재 기능을 위해 다음 데이터를 수집·저장하지 않는다.

- Wi-Fi SSID, BSSID, Wi-Fi MAC
- Bluetooth MAC 및 주변 Bluetooth 기기 목록
- Wi-Fi 접속 이력
- 사용자 이동 경로와 과거 접속 장소

- **MUST** 새로운 보안 기능을 이유로 영구적인 사용자 추적 데이터를 축적하지 않는다.
- **MUST** 수집 항목뿐 아니라 명시적인 비수집 항목도 정책으로 관리한다.
- **MUST** 모니터링을 이유로 불필요한 개인정보를 수집하지 않는다.

## 9. 인증, 세션과 비밀정보

- **MUST** User 데이터와 인증정보를 분리한다.
- **MUST** API Key, DB Password와 Secret을 소스코드에서 분리한다.
- **MUST** 비밀번호를 평문으로 저장하지 않는다.
- **MUST** 인증·세션 토큰 원문을 로그에 기록하지 않는다.
- **MUST** 안정적인 내부 `user_id`와 외부 세션 식별자를 분리한다.
- **MUST** 외부 세션 식별자에 순차번호나 예측 가능한 ASCII 규칙을 사용하지 않는다.
- **MUST** 세션 식별자는 암호학적으로 안전한 난수 기반 opaque identifier로 생성한다.
- **MUST** 로그인, 재인증, 토큰 갱신 등 적절한 보안 경계에서 세션 식별자를 회전하고 만료·로그아웃 시 폐기한다.
- **MUST** 영구적인 기기 물리 식별자를 사용자 추적 수단으로 사용하지 않는다.
- **SHOULD** 내부 `user_id`를 외부에 불필요하게 노출하지 않는다.

## 10. 관측 가능성

운영 성숙도에 따라 다음 지표를 관찰할 수 있어야 한다.

- 시스템: 오류율, 처리시간, API 상태
- 데이터: 수집 성공·실패, 중복 제거율, Evidence 부족 Event
- AI: 호출 수, 토큰, 비용, 실패율, cache hit rate
- 전달: Alert 성공·실패

관측 데이터에는 민감정보, 인증 토큰 원문 또는 불필요한 사용자 식별정보를 포함하지 않는다. 로그와 지표의 보존 기간 및 접근 권한은 운영 환경에 맞게 정의해야 한다.

## 11. 품질과 운영 원칙

- **MUST** 데이터 공급자 장애와 AI 공급자 장애가 핵심 데이터의 정합성을 훼손하지 않게 한다.
- **MUST** 재처리와 재시도는 중복 Event, Assessment 또는 Alert를 만들지 않도록 멱등성을 고려한다.
- **SHOULD** 외부 연동 실패와 내부 분석 실패를 구분해 관찰한다.
- **SHOULD** 핵심 결정과 정책 버전을 결과에 연결해 재현 가능성을 높인다.
- **SHOULD** 단일 개발자가 로컬에서 핵심 흐름을 재현하고 운영 문제를 진단할 수 있게 한다.

## 12. 변경 관리와 개발자 규칙

개발자는 구현 전에 이 문서와 관련 ADR을 확인한다. 요구사항이 Architecture와 충돌하면 즉시 구현하지 않고 충돌 내용, 위험과 선택지를 먼저 보고한다.

다음 변경은 ADR 또는 이에 준하는 명시적 승인 없이 수행하지 않는다.

- 보안 정책 완화
- 개인정보 수집 확대
- AI 호출 또는 비용을 구조적으로 증가시키는 변경
- 외부 서비스 종속성 증가
- 핵심 데이터 모델 및 모듈 경계 변경

중요한 Architecture 결정은 이유 없이 기존 기록을 덮어쓰지 않는다. ADR에는 최소한 `Context`, `Decision`, `Alternatives Considered`, `Consequences`를 기록한다. 기존 결정을 변경할 때는 새 ADR로 대체 관계를 명시한다.
